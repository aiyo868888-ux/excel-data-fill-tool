# 我的"氛围编程"血泪史

**来源**：清新研究
**日期**：2026年1月22日
**链接**：https://mp.weixin.qq.com/s/CALekf9EKfhrgbechRoXpQ

---

最近，我彻底沉迷进了**"氛围编程"（Vibe Coding）**——那种用自然语言指挥AI写代码的快感，真的会上瘾。

一句"帮我写个网页，能上传Zip文件在线解压"，几分钟后就有一个能用的工具诞生；再来一句"把图片切成九宫格"，又一个完美小玩意儿出炉。那种即时反馈的爽感，简直像开了挂。

但当我试图用同样的方式去造一个真正复杂的后端项目（带数据库、用户系统、订阅功能）时……现实给了我狠狠一击。

代码开始疯狂膨胀，bug层出不穷，上下文一长AI就"迷失"，改个小功能能牵扯出十几个文件，改完又引入新问题。最后项目卡在3万行，差点让我放弃。

我花了整整三个月，反复试错、翻车、再优化，终于摸出了一套**能从玩具级小工具，稳定进化到生产级大项目的完整工作流**。

---

## 第一阶段：蜜月期，谁都可以当造物主

氛围编程最魔性的地方在于——**它把编程门槛拉低到几乎为零**。

你不需要记得语法、分号、类型声明，只需要说清楚"我想要什么"：

- 去除Markdown转纯文本？
- 批量压缩图片？
- 在线JSON格式化工具？

一句话扔给AI，基本就能跑。反馈是即时的、视觉化的，改起来也几乎零成本。

这阶段**关键词是：无状态、单文件、小逻辑**。

你会进入一种极致的"心流"状态：灵感来了 → 立刻实现 → 立刻看到效果 → 更兴奋 → 再来一个。

普通人也能在一晚上做出十几个实用小工具，第一次体会到"造物"的快乐。

---

## 第二阶段：熵增地狱，代码开始失控

但当你想做真正的产品，代码量突破几千行、几万行，需要数据库、认证、状态管理、多端同步时……一切都变了。

**常见崩溃场景：**

- AI记不住全局上下文，改登录逻辑时把三套验证系统搞混
- 每次修bug都"安全起见"加一层try-catch或新函数，代码迅速臃肿
- 旧代码不敢删，留下大量"僵尸代码"
- 依赖随便装，package.json像垃圾场
- **最要命的**：AI偷偷在终端跑了npm install或改了配置文件，你根本不知道，换台机器直接崩

这就是"熵增"：系统无序度飞速上升，维护成本指数级爆炸。

很多人（包括曾经的我）在这阶段直接放弃，认为"AI写代码只是玩具"。

---

## 第三阶段：破局——成为AI的"总工程师"

真正的转折点在于：**你得从"指令发出者"变成"系统管理者"**。

我现在的工作流叫 **Architect-Builder 双模态**：

### 1. 架构师阶段（推荐用 Gemini / Claude）

先不写代码，而是让AI输出一份完整的技术设计文档（TDD）：

这份文档就是"施工图纸"。

- 数据表怎么改？
- 新增哪些API？
- 前端组件如何调整？
- 怎么保持DRY和现有系统兼容？

### 2. 建设者阶段（推荐用 Cursor 执行）

把图纸喂给Cursor，让它严格按步骤实现。

Cursor不需要理解整个项目，只需专注当前任务，出错概率大幅降低。

## AI 协作角色分工指南

| 维度 | 架构师 (The Architect) | 建设者 (The Builder) |
|------|------------------------|----------------------|
| **推荐模型** | Gemini 3 Pro, Claude 3 Opus | Cursor (Claude 3.5 Sonnet), Copilot |
| **核心能力** | 超长上下文 (1M+ Token)，逻辑推理，全局规划 | 极速代码生成，IDE 集成，文件读写 |
| **输入数据** | 整个代码库结构，需求文档，技术栈约束 | 具体的文件片段，详细的实现指令 |
| **输出产物** | 技术设计文档 (TDD)，迁移计划，伪代码 | 可执行的 .ts / .py 文件，Bug 修复补丁 |
| **典型指令** | "分析当前鉴权模块，设计一套迁移到 Supabase 的方案。" | "根据 TDD 文档第 3 节，实现 UserAuth 类。" |

---

## 协作工作流建议

### 1. 架构师先行
利用大上下文模型（如 Gemini）对全库代码进行体检，输出一份详细的 TDD（技术设计文档）。

### 2. 建设者落地
将 TDD 文档放入 Cursor 的 Context（或 Composer 模式）中，让 AI 根据文档的具体章节进行精准的模块化编写。

**同时配合三大硬核习惯：**

- 项目根目录放一个 `context.md` 或 `active_task.md`，记录当前目标、约束、已完成事项——相当于给AI装"外置记忆"
- 一个功能点对应一个新聊天窗口，避免上下文污染
- 配置 `.cursorrules` 强制AI遵守规则：不写超过300行单文件、必须DRY、禁止硬编码key、旧代码直接删…

## 部署环节的黄金法则

部署环节，我彻底抛弃了"手动上传"的原始方式，改用 **GitHub + Vercel + Supabase** 的黄金三角：

- **GitHub 是"真理之源"**：所有代码、数据库迁移文件都版本化，push 到 main 自动触发 Vercel 部署
- **数据库迁移**绝不让AI直接操作生产库，而是生成 migration 文件，随代码一起提交，CI/CD 时自动 supabase db push
- **所有密钥**（Supabase Key、OpenAI Key）本地放 .env.local（加进 .gitignore），生产在 Vercel 面板手动填，代码里强制用 process.env 读取
- **上线前必做一次AI审计**：让Gemini/Claude审查全项目，检查硬编码key、console.log泄露、RLS策略、未使用依赖，有效避免"误伤关键代码"和安全漏洞

做完这些后，我终于能用氛围编程稳稳地造出**生产级、带数据库、支持订阅的复杂SaaS**，而且代码干净、可维护。

---

## 结语

氛围编程不是让编程"变简单"，而是把人类的认知从"怎么写代码"解放出来，**去专注"代码要解决什么问题"和"系统如何组织"。**

未来，代码不再是手艺活，而是工业化生产。而你，将是这座AI工厂的**总工程师**。

如果你也正在或准备用AI写代码，强烈建议收藏这套方法论——它能帮你少走90%的弯路。

2026年，AI编程才刚刚开始。我们一起，**把灵感变成真实的产品吧**。

### 关键提示词模板（Prompt Templates）

#### 1. 架构设计（推荐使用 Gemini 3 Pro）

```
你是一名资深系统架构师。我需要为当前项目添加一个'用户订阅'功能。请阅读现有的数据库 Schema（已附）和代码结构。不要直接写代码，而是输出一份《技术设计文档》，包含：

1. 需要修改的数据库表结构；
2. 新增的 API 端点定义；
3. 前端组件的修改计划。

请确保方案符合 DRY 原则，并考虑到与现有 Auth 模块的兼容性。
```

#### 2. 代码清理（推荐使用 Cursor）

```
分析 utils/helpers.ts 文件。找出其中重复的逻辑或未使用的函数。请基于 DRY 原则进行重构，并删除所有死代码。在修改前，先列出你要删除的函数名，经我确认后再执行。
```

#### 3. 部署检查（推荐使用 Claude）

```
我要将项目部署到 Vercel。请检查我的 next.config.js 和 package.json，确保构建脚本（build script）配置正确。同时，请根据代码中的引用，列出我需要在 Vercel 后台配置的所有环境变量清单。
```
